---
name: Drive Wiki sync boundary
description: Durable ownership boundaries and scheduling rules for the Google Drive PDF-to-Wiki sync.
---

Access Google Drive through a Google Cloud service account (lib/googleServiceAccount.ts), authenticated with a hand-rolled RFC 7523 JWT-bearer token exchange -- never through Replit's connector SDK/proxy, and never through a per-admin OAuth flow. The existing Python script (scripts/drive_wiki_sync.py) remains the incremental manifest comparison and PDF text-extraction engine; synced results are committed to the Wiki database rather than maintained as a second runtime JSON source.

**Why:** This feature previously used `@replit/connectors-sdk`'s `ReplitConnectors().proxy("google-drive", ...)`, which hard-requires a `REPL_IDENTITY` environment variable only ever present inside Replit's own execution environment (confirmed by reading the SDK's source). That broke the feature entirely once this app moved to running as a Cloudflare Worker + Container, which has no such variable and no access to Replit's connector proxy. A service account was chosen over per-admin OAuth (the pattern used for Planning Center) because this sync is a background job with no "signed-in user" context -- it needs to run from a Cron Trigger with nobody logged in, and a service account's token never needs a person to re-authorize it. The target Drive folder must be shared with the service account's `client_email` for this to work.

**How to apply:** Pass Drive metadata and changed PDF paths into the script's manifest mode. Keep manual Wiki content distinct from Drive-managed records, abort the whole apply on extraction failures, and use the durable database lease for every manual or scheduled run. Do not reintroduce `@replit/connectors-sdk` or any other Replit-specific SDK/env var (`REPL_IDENTITY`, `REPLIT_CONNECTORS_HOSTNAME`, etc.) into this path -- this app's production runtime is Cloudflare, not Replit.

Production's guaranteed daily execution is a Cloudflare Cron Trigger (`"0 6 * * *"` in wrangler.toml's `[triggers] crons`) calling `POST /api/admin/wiki-drive-sync/run-scheduled` (routes/adminWikiDriveSync.ts), authenticated with the `WIKI_DRIVE_SYNC_RUN_SECRET` shared secret -- the same pattern Weekly Pulse uses for its own Monday Cron Trigger. This replaced an earlier design that relied on a Replit Scheduled Deployment invoking the standalone `sync:wiki-drive` script (`wikiDriveSyncJob.ts`); that script still exists and still works (it just calls the same `runWikiDriveSync()`), but nothing in the current Cloudflare architecture invokes it, so don't assume it's what's actually running production's daily sync. The container's own `startWikiDriveScheduler()` (an hourly "run if due today" check, started from index.ts) remains in place as a catch-up fallback only, because a scale-to-zero Container can't guarantee it's awake at any particular moment -- it is not the guaranteed path.

**Why:** Multiple autoscaled instances can overlap and may be idle at the scheduled time, and Cloudflare Cron Triggers reach the Container the same way a Worker request does (there's no separate scheduler product to depend on, the way Replit's was).

**How to apply:** Use the same `runWikiDriveSync()` call and database lease for every execution path (manual admin "run now", the Cron-triggered scheduled route, and the hourly in-process fallback) -- never create a separate synchronization implementation.
